# بازبینی کامل کد — Ram Optimizer Service

> این سند بازبینی نسخه‌ی ۱ است. بخش‌های ۱ تا ۴ تحلیل اولیه‌اند و بخش ۵
> گزارش اجرای همه‌ی موارد در نسخه‌ی ۲ است.
> ارجاع‌های بخش‌های ۱–۴ به نسخه‌ی ۱ (تک‌فایل) هستند: `ram_optimizer.py` حالا
> به پکیج `ramopt` منتقل شده و `ram_optimizer_service.py` فقط نقطه‌ی ورود exe است.

## خلاصه‌ی مدیریتی

منطق پایه درست و از APIهای رسمی ویندوز استفاده شده (`EmptyWorkingSet` +
`NtSetSystemInformation`)، اما سه ضعف ساختاری دارد:

1. **معیار تصمیم‌گیری اشتباه است** — `psutil.virtual_memory().percent` در ویندوز
   کش (Standby List) را هم «مصرف‌شده» حساب می‌کند؛ یعنی برنامه بر اساس عددی
   تصمیم می‌گیرد که تقریباً همیشه بالا است.
2. **هیچ محافظی در برابر رفتار خودتخریب‌گر وجود ندارد** — بدون cooldown، بدون
   سقف تعداد پاک‌سازی، بدون لیست استثنا؛ روی سیستمی که همیشه بالای آستانه است،
   هر ۶۰ ثانیه کش ویندوز را پاک می‌کند و نتیجه‌اش کندتر شدن سیستم است.
3. **گزارش‌ها گمراه‌کننده‌اند** — عدد «آزادشده» از همان معیار اشتباه محاسبه
   می‌شود و تابع حتی وقتی هیچ پروسه‌ای پاک نشده `True` برمی‌گرداند.

## ۱) باگ‌ها

### 🔴 بحرانی

**B1 — آستانه در کد ۵۵٪ است، در مستندات ۷۵٪**
`ram_optimizer.py:44` مقدار `MEMORY_THRESHOLD_PERCENT = 55` دارد، ولی
`README.md:7` و `README.md:127` می‌گویند ۷۵٪. عملاً برنامه با آستانه‌ای
۱۰ واحد کمتر از آنچه کاربر فکر می‌کند کار می‌کند.

**B2 — معیار «مصرف رم» از نظر فنی غلط است**
از سورس psutil ویندوز: `percent = (total - avail) / total` و `avail` همان
`PhysicalAvailable` ویندوز است که در مستندات مایکروسافت «مجموع Standby، Free و
Zero list» است. یعنی **حافظه‌ی کش هم مصرف‌شده شمرده می‌شود**. یک ویندوز کاملاً
بیکار با کش فایل بزرگ، ۸۰٪ «مصرف» نشان می‌دهد در حالی که commit واقعی شاید
۲۰٪ باشد. نتیجه:
- تریگر بر اساس کش بالا می‌زند، نه فشار واقعی حافظه.
- بدتر: خالی کردن Standby List خودِ همین عدد را بالا/پایین می‌برد → یک حلقه‌ی
  بازخورد که باعث می‌شود ابزار «انگار دارد کار می‌کند».

**B3 — عدد «آزادشده» بی‌معنا است**
`ram_optimizer.py:286`: `freed_mb = mem_before.used - mem_after.used`. چون
`used` شامل کش است، این عدد نوسان کش را نشان می‌دهد نه حافظه‌ی واقعاً آزادشده،
و با `max(0, ...)` هر مقدار منفی پنهان می‌شود. باید از
`VirtualQuery`/`GetProcessMemoryInfo` قبل و بعد از trim اندازه‌گیری شود.

**B4 — بدون cooldown و سقف عملیات**
`ram_optimizer_service.py:112-122`: هر ۶۰ ثانیه، اگر درصد بالای آستانه باشد،
دوباره و دوباره پاک‌سازی کامل انجام می‌شود. روی لپ‌تاپی که پس از بوت همیشه ۶۰٪+
است، این یعنی هر دقیقه: صدها `OpenProcess` + خالی کردن کش دیسک → I/O اضافه،
افت کارایی، مصرف باتری. هیچ هیسترزیس (trigger/reset جدا)، هیچ فاصله‌ی حداقل و
هیچ سقف «حداکثر N بار در ساعت» وجود ندارد.

**B5 — تابع موفقیت را حتی در شکست کامل برمی‌گرداند**
`ram_optimizer.py:269-296`: اگر `trimmed == 0` و `purge_standby_list()` هم
`False` باشد، باز هم `True` برمی‌گردد و لاگ «پاک‌سازی انجام شد» می‌نویسد. یعنی
روی سیستمی که برنامه هیچ کاری نمی‌تواند بکند، لاگ می‌گوید همه‌چیز خوب است.
همچنین هیچ آماری از «چند پروسه Access Denied خورد» ثبت نمی‌شود.

### 🟠 مهم

**B6 — خطای NTSTATUS دور ریخته می‌شود**
`ram_optimizer.py:250-256`: خروجی `NtSetSystemInformation` فقط به bool تبدیل
می‌شود؛ علت شکست (مثلاً `STATUS_PRIVILEGE_NOT_HELD = 0xC0000061`) در لاگ
نمی‌آید. برای عیب‌یابی سرویس روی سیستم کاربر، این مهم‌ترین اطلاعات است.

**B7 — اختیارهای اشتباه/اضافی فعال می‌شوند**
`ram_optimizer.py:94-98`: `SeIncreaseQuotaPrivilege` فعال می‌شود، ولی مستندات
همان کلاس اطلاعاتی (`ProcessQuotaLimits`) برای *تنظیم*،
`SeIncreaseWorkingSetPrivilege` (یا `SeIncreaseBasePriorityPrivilege`) می‌خواهد.
همچنین `SeDebugPrivilege` برای این کار لازم نیست و فعال کردنش در یک سرویس،
یکی از رایج‌ترین تریگرهای آنتی‌ویروس/EDR است.

**B8 — هیچ لیست استثنا و هیچ اولویت‌بندی وجود ندارد**
`ram_optimizer.py:226-247`: همه‌ی پروسه‌ها به یک چشم trim می‌شوند، شامل
`dwm.exe`، برنامه‌ی تمام‌صفحه (بازی)، آنتی‌ویروس و برنامه‌ای که همین حالا
استفاده می‌شود. trim روی برنامه‌ی فعال = لگ و خواندن مجدد از دیسک. ضمناً
پروسه‌های کوچک (زیر ~۲۰ مگابایت working set) هم باز می‌شوند که سودش صفر و
هزینه‌اش صدها syscall است.

**B9 — ترتیب پاک‌سازی بهینه نیست**
`ram_optimizer.py:281-283`: بعد از trim بلافاصله Standby List هم خالی می‌شود،
حتی اگر همان لحظه RAM کافی آزاد شده باشد. درست‌تر: اول trim، اندازه‌گیری، و
خالی کردن کش فقط اگر هنوز زیر هدف هستیم.

**B10 — کرش‌لاگ بی‌نهایت رشد می‌کند**
`ram_optimizer_service.py:31-45`: فایل `crash.log` هیچ چرخش/سقفی ندارد (برخلاف
لاگ اصلی). یک باگ تکراری می‌تواند کل درایو سیستم را پر کند. همچنین
`sys.excepthook` خطاهای داخل ترد را نمی‌گیرد (فعلاً تردی نیست، ولی اگر اضافه شود).

**B11 — لاگ‌ها سطح INFO هستند، پس همه‌ی `logger.debug` مرده‌اند**
`ram_optimizer.py:194` (`setLevel(logging.INFO)`) در حالی که مهم‌ترین اطلاعات
عیب‌یابی (`ram_optimizer.py:277`, `:295`) با `debug` ثبت می‌شوند. یعنی نه در
لاگ فایل هستند و نه قابل فعال‌سازی بدون تغییر کد/بیلد.

**B12 — سرویس از کار افتاده دوباره بالا نمی‌آید**
هیچ‌جای پروژه `sc failure` اجرا نمی‌شود و `install_service.bat` هم فقط
`--startup auto` می‌دهد. اگر سرویس کرش کند، ویندوز هیچ تلاشی برای ری‌استارت
نمی‌کند (سیاست پیش‌فرض: بدون اقدام). ضمناً `auto` به‌جای `delayed-auto` یعنی
رقابت با سرویس‌های دیگر در زمان بوت.

**B13 — تسک Task Scheduler روی لپ‌تاپ کار نمی‌کند و بعد از ۳ روز می‌میرد**
`install_task.bat:24`: با `schtasks /Create` مقادیر پیش‌فرض ویندوز اعمال می‌شوند:
`DisallowStartIfOnBatteries = True` و `ExecutionTimeLimit = PT72H`. یعنی روی
لپ‌تاپ اگر لحظه‌ی بوت روی باتری باشد تسک اجرا نمی‌شود، و اگر اجرا شود ویندوز
بعد از ۷۲ ساعت آن را می‌کشد — برای یک دیمن دائمی فاجعه است.

**B14 — کوتیشن‌گذاری `/TR` در `install_task.bat` شکننده است**
الگوی `\"%EXE%\" console` در cmd استاندارد نیست و اگر مسیر فاصله داشته باشد
(`C:\Program Files\...`) خطای «Invalid argument/option» می‌دهد. راه درست:
`Register-ScheduledTask` در PowerShell یا فایل XML.

**B15 — فایل `.spec` مرده است و با بیلد واقعی هم‌خوان نیست**
`build_exe.bat:42-48` از آرگومان‌های CLI استفاده می‌کند و `RamOptimizerService.spec`
را نادیده می‌گیرد. هر تغییری در spec هیچ اثری ندارد و دو منبع حقیقت ایجاد شده.

**B16 — `pyinstaller` جزء نیازمندی‌های زمان اجراست**
`requirements.txt:3`: کسی که فقط می‌خواهد با پایتون اجرا کند، مجبور به نصب
PyInstaller می‌شود. باید `requirements-dev.txt` جدا شود. ضمناً هیچ نسخه‌ای pin
نشده (بیلد غیرقابل تکرار).

**B17 — بدون `.gitignore`**
`__pycache__/`، `build/`، `dist/`، `release/` هیچ‌کدام ignore نیستند.

## ۳) برای «حرفه‌ای شدن» چه چیزهایی کم است

### ۳-۱. سیاست هوشمند جای آستانه‌ی درصدی
- تصمیم‌گیری بر پایه‌ی **فشار واقعی**: `MEMORYSTATUSEX` (percent of committed
  memory, available MB) + شمارش `ModifyList`/`StandbyList` با
  `NtQuerySystemInformation(SystemMemoryListInformation)` — دقیقاً همان چیزی که
  RAMMap نشان می‌دهد.
- **هیسترزیس**: شروع در X٪، خاموش شدن تا پایین آمدن به Y٪ (مثلاً ۸۵ / ۷۰).
- **Cooldown** (مثلاً ۵ دقیقه) و **سقف** (مثلاً ۶ بار در ساعت) و **بک‌آف
  تصاعدی** اگر پاک‌سازی سودی نداشت.
- **هدف مطلق**: «تا وقتی حداقل ۲ گیگابایت free هست کاری نکن» — روی سیستم ۶۴
  گیگی این تنها منطق درست است.

### ۳-۲. رفتار محترمانه با کاربر
- لیست استثنا (نام پروسه + wildcard) با پیش‌فرض‌های امن: `dwm`, `csrss`,
  `lsass`, `winlogon`, `services`, `MsMpEng`, آنتی‌ویروس‌ها.
- تشخیص برنامه‌ی **تمام‌صفحه/بازی** و توقف موقت پاک‌سازی.
- توقف روی **باتری** (قابل تنظیم).
- «ساعات سکوت» و پرهیز از پاک‌سازی هنگام بکاپ/رندر سنگین (تشخیص I/O بالا).
- حالت `--dry-run` که فقط گزارش می‌دهد چه کاری می‌کرد.

### ۳-۳. شفافیت و پایش
- فایل `status.json` در ProgramData: آخرین اجرا، آخرین خطا، RAM فعلی،
  مجموع آزادشده، آپ‌تایم — تا هر ابزار مانیتورینگی بتواند بخواند.
- ثبت در **Event Log ویندوز** با Source Name واقعی (نه پیام‌های عمومی SCM) تا
  در Event Viewer قابل فیلتر باشد.
- لاگ ساختاریافته JSON (اختیاری) + لاگ چرخشی برای `crash.log`.
- دستور `status` در CLI و یک آیکون **تِرِی** سبک (pystray) با «آزادسازی الان» و
  «توقف موقت» — بیشتر کاربران ویندوز بدون tray، سرویس را «مرده» فرض می‌کنند.

### ۳-۴. مهندسی و انتشار
- بازآرایی به پکیج: `ramopt/core/memory_win32.py`, `policy.py`, `config.py`,
  `logging_setup.py`, `service.py`, `cli.py` + `pyproject.toml` با entry point.
- **تست**: pytest با لایه‌ی mock برای `ctypes`/`win32` (الان صفر تست وجود دارد)
  و CI روی `windows-latest`: ruff + mypy + pytest + ساخت exe + اجرای
  `--once --dry-run`.
- نسخه‌بندی معنایی، `--version`, `CHANGELOG.md`, README انگلیسی، `.gitignore`.
- **نصب‌کننده واقعی** (Inno Setup یا MSI) با: حذف تمیز، بستن سرویس قبلی،
  ثبت Event Source، حذف ProgramData، و پشتیبانی از ارتقا (upgrade) بدون خطا.
- **امضای دیجیتال** کد (حداقل گواهی OV ارزان) — تنها راه واقعی حل هشدار
  SmartScreen/آنتی‌ویروس برای ابزارهایی که `OpenProcess` روی همه‌ی پروسه‌ها
  می‌زنند. بدون امضا، این برنامه همیشه بدافزار-مانند دیده می‌شود.
- بیلد قابل تکرار (pin کردن نسخه‌ها، `--clean`، SBOM) و انتشار GitHub Releases
  با checksum.

### ۳-۵. صداقت فنی در محصول
- README فعلی یک نکته‌ی صادقانه خوب دارد؛ حرفه‌ای‌ترش این است که در خود
  برنامه هم «سود واقعی» گزارش شود: چند مگابایت از Working Set آزاد شد، چند
